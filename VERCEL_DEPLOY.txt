GITHUB DESKTOP PREPARATION
--------------------------
1. Extract the complete project archive into a dedicated folder.
2. In GitHub Desktop choose File → Add Local Repository and select that project folder.
   If it is not yet a Git repository, choose Create a Repository here and use the
   existing project folder as the repository root. Do not nest a second project folder.
3. Confirm .env.example is present but no .env, .env.local, .env.production,
   provider secrets, node_modules, .next, or .vercel folders are staged.
4. Run: node scripts/audit-project-integrity.mjs
5. Do not treat this source snapshot as deployable until the official pi-backend dependency graph has
   been generated by npm in a registry-connected supported Node environment and
   reviewed. Do not hand-edit package integrity values. A GitHub review branch may be pushed, but CI/Vercel install is expected to fail until this is repaired.
6. After all release gates pass, commit the reviewed source + package-lock changes
   and push the intended branch. A GitHub push is not production approval.

ENVIRONMENT ISOLATION
---------------------
Use separate Vercel Preview/Testnet and Production/Mainnet environment values.
Never share a Mainnet Pi API key or Mainnet Supabase service-role key with Preview,
and never point Production at the Testnet Supabase project. Keep all server keys in
Vercel server-side environment settings, never in NEXT_PUBLIC_* variables or Git.
Use .env.example only as a variable-name template; never fill it with real secrets.

Set the public Pi network selector explicitly for each deployment target:
- Preview / Testnet: `NEXT_PUBLIC_PI_SANDBOX=true` and Testnet Pi server credentials.
- Production / Mainnet: `NEXT_PUBLIC_PI_SANDBOX=false` and Mainnet Pi server credentials.

Pi network variables must match the Pi Developer Portal app assigned to each
Vercel environment:
- Preview / Testnet: NEXT_PUBLIC_PI_SANDBOX=true
- Production / Mainnet: NEXT_PUBLIC_PI_SANDBOX=false

Confirm NEXT_PUBLIC_PI_CLIENT_ID, PI_API_KEY, and Supabase URL/service-role values
independently for Preview and Production before testing. Do not enable A2U or
bank/GHC payouts until the specific provider and database gates pass.

DOMAIN VALIDATION
-----------------
The source maps /validation-key.txt to /api/validation-key. Validate the behavior
against the current Pi Developer Portal configuration before release. Do not commit
validation text or introduce a second validation mechanism during repository cleanup.
The current API route returns HTTP 503 when its existing server-side key value is
not configured, so domain validation must be reconciled and explicitly tested before
promotion. This runbook does not instruct you to add or restore a new environment
variable as a substitute for verifying the actual registered app setup.
