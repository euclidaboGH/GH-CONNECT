# GreenHaven / GH Connect — coordinated product transformation roadmap

This is the approved **11-priority product roadmap**. The product priorities below are the user's sequence; older engineering phase labels (for example Phase 7/8/9 in historical worklogs) are implementation-history labels and must not reorder this roadmap. Each area is redesigned as part of one coherent product: shared navigation, design language, identity, permissions, financial truth, accessibility, and cross-surface journeys must remain consistent.

## Critical Wallet trust follow-up

This is a cross-cutting financial-safety issue and must be resolved before production approval, even while the product roadmap proceeds to Rewards.

1. **Pi available/reserved:** trace authoritative ledger movements, reservation rows, pending/expired/cancelled/failed transaction states and snapshot reconciliation. Do not relabel reserved funds as available or release legitimate holds from client code. Reconcile each affected user's authoritative records and provider/payment state before any correction.
2. **Six-digit PIN discoverability:** the current source exposes a six-digit *withdrawal PIN* creation flow inside the Pi withdrawal sheet (`components/ghc/pi-withdraw-sheet.tsx`). The general Settings screen's PIN is a separate device-unlock PIN, not the financial withdrawal PIN. Add a clearly named Wallet security/settings entry and explain the distinction; preserve server-side hashing/verification, request-bound proof, rate limits, recovery controls and fail-closed behavior. Never store or log plaintext PINs.
3. **Scope:** verify whether other protected actions require the same PIN or a distinct authorization factor before changing labels or sharing PIN policy across send, marketplace, rewards or checkout. Do not silently broaden a withdrawal PIN into a universal transaction PIN.
4. **Acceptance:** test available → reserved → released/settled transitions, cancellation/expiry/failure, duplicate reservation prevention, two-session concurrency, PIN creation/confirmation, wrong PIN/rate limiting, recovery and request-bound authorization. Testnet reconciliation and operator sign-off are required.

## Current release increment — Priority 3 Rewards + Wallet trust UX (0.330.24)

This source increment adds a dedicated Wallet withdrawal-PIN manager that reads status from the existing authenticated endpoint, permits first-time setup only when the server explicitly confirms no PIN exists, requires two matching six-digit entries, and reuses the existing server-side hash/rate-limit/insert-only policy. Existing recovery remains available for configured PINs. The Wallet Pi balance copy now distinguishes total available from eligible-to-withdraw and reserved-for-requests amounts, and explains that only unstarted payout requests can be released; provider-started requests require reconciliation. Rewards now separates locally tracked claim-ready counts from under-review counts, includes approved holds in the pending summary, and explains that verified missions unlock achievements but do not issue GHC or Pi under the current policy. No ledger, balance, issuance, payout, provider, or migration authority changed.

This increment does not resolve individual users' Pi reservations. That requires authenticated ledger entries, payout request states and provider results for each affected account; never bulk-release or relabel reserved funds from UI code.

## Priority 3 — Rewards transformation sequence

1. **Rewards home:** show GHC and Pi separately; distinguish available, pending, locked, claimable and already credited values. Unknown or unavailable values remain unknown, never fabricated zeroes.
2. **Missions and progress:** explain mission criteria, verified progress, exclusions, deadlines and evidence. Durable completion is server-verified; any local journey guidance must be clearly labelled as non-authoritative and never treated as proof.
3. **Claims:** make eligibility, claim action, processing, duplicate/retry behavior, failure and support paths understandable. Server/database remains the only issuance authority.
4. **Reward transparency:** distinguish GHC rewards from Pi cashback; show pending, maturity, validation and ledger-confirmed credit as separate states. A reward is credited only when the authoritative ledger confirms it.
5. **History and insights:** reconcile authenticated history with the canonical ledger, disclose when a read is incomplete or unavailable, and provide meaningful search/filter/receipt details without aggregating different assets.
6. **Abuse and release gates:** preserve idempotency, durable rate limits, ownership, RLS and service-role isolation; review the mission-verification migration against remote histories and a disposable database before Testnet application.

## Global design and engineering rules

- Redesign journeys across connected surfaces, not isolated screens. Reuse canonical components, APIs, routes and domain authorities.
- Keep GHC and Pi separate assets and separate ledgers. Never sum or convert them for display without an explicitly authorized conversion contract.
- Server-confirmed balances, transaction states, entitlements, mission eligibility, reward issuance and checkout/payment outcomes are authoritative. Local state is presentation/cache only.
- Preserve session identity, ownership, step-up, idempotency, durable rate limits, RLS, service-role boundaries, privacy, block/mute and moderation policy.
- No client-side minting, transfer execution, payout, refund, escrow release, treasury movement, settlement or payment completion.
- No migration is applied from source review alone. Reconcile each target database's remote history and validate on disposable PostgreSQL/Testnet before approved application.
- Every release distinguishes source checks from Node 24 build, browser/device, live provider/database and operator acceptance. Production is not approved until all required gates pass.

## Priority 6 — Settings transformation (0.330.29)

Settings now opens with a coordinated control-centre overview that summarizes privacy posture, enabled notification categories, locale and appearance, with direct routes into the relevant control surfaces. Existing account/economy, privacy/safety, preference, performance, support and legal subsections remain the canonical destinations rather than being duplicated into a new settings implementation.

Settings mutations now send narrow partial patches instead of spreading a render-time snapshot across the whole settings object. This prevents rapid independent toggles from overwriting one another with stale values. Discovery radius is clamped to its supported range, and age bounds are constrained against one another. Existing messaging privacy continues to require the authenticated server preference endpoint; other settings continue through the existing user-state persistence lane. No new privacy authority, notification delivery promise, permission grant, migration or financial authority is introduced.

Priority 6 source transformation is complete for this increment. Node 24.15.x dependency-backed typecheck/lint/build, browser/device accessibility, cross-session persistence and live privacy acceptance remain required before production approval.
